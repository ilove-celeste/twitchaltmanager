# Twitch Alt Manager 🎮

Быстрое переключение между аккаунтами Twitch — без ввода паролей и кодов из почты.

## Как это работает

Расширение сохраняет **cookies сессии** каждого аккаунта локально (зашифровано через AES-256-GCM).  
При переключении — просто подменяет куки и перезагружает вкладки Twitch.  
Никаких паролей не хранится. Данные не покидают браузер.

---

## Установка (ungoogled-chromium)

1. Распакуй папку `twitch-alt-manager` в удобное место (например, `C:\extensions\twitch-alt-manager`)
2. Открой `chrome://extensions/`
3. Включи **«Режим разработчика»** (Developer mode) — переключатель вверху справа
4. Нажми **«Загрузить распакованное расширение»** (Load unpacked)
5. Выбери папку `twitch-alt-manager`
6. Расширение появится в панели

> **Важно для ungoogled-chromium:** если при установке появляется ошибка о подписи — это нормально для режима разработчика. Просто подтверди установку.

## Первое использование

### Сохранить аккаунт

1. Войди в нужный аккаунт Twitch в браузере как обычно
2. Открой попап расширения (иконка в панели)
3. Нажми **«+ Сохранить»**
4. Введи имя (или оставь как есть — подтянется из куков)
5. Нажми **«Сохранить»**
6. Повтори для каждого аккаунта

### Переключиться

- Просто **кликни по нужному аккаунту** в попапе
- Страницы Twitch перезагрузятся — ты уже под новым аккаунтом

### Обновить сессию

Если сессия протухла (Twitch попросил снова войти):
1. Войди вручную в браузере
2. В попапе нажми иконку 🔄 рядом с аккаунтом
3. Расширение перезапишет куки свежими

## FAQ

**Почему нужно сохранять каждый аккаунт вручную один раз?**  
Расширение не знает пароли — оно работает с cookies. Нужно войти в аккаунт хотя бы один раз, чтобы Twitch выдал куки сессии.

**Безопасно ли это?**  
Куки хранятся только локально в `chrome.storage.local` в зашифрованном виде (AES-256-GCM). Ключ шифрования генерируется браузером и тоже хранится локально. Никакие данные никуда не отправляются.

**Что если Twitch добавил 2FA?**  
2FA проверяется при **входе**, а не при каждом запросе. Если ты уже вошёл и сохранил куки — переключение не потребует 2FA.

**Куки протухают?**  
Расширение продлевает срок action-кук при сохранении (+30 дней). Но если Twitch принудительно инвалидирует сессию — придётся войти заново и обновить сессию кнопкой 🔄.

### Найдено при свежем разборе (не было в исходном ревью)

- **Ложно-успешный статус для истёкших cookies** (уточнение к п.2): `chrome.cookies.set()` мог вернуть «успех» для cookie с уже прошедшим `expirationDate`, хотя браузер тут же его удаляет. Теперь такие cookies **пропускаются проактивно** до вызова `set()`, плюс добавлена **повторная проверка** (`verifyCookies`) фактического наличия критичных cookies после установки.
- Реальный отказ `chrome.tabs.reload()` (не факт неуспеха самого переключения) теперь долетает до пользователя отдельным сообщением, а не тонет в `catch(_){}`.
- `chrome.cookies.remove()`, возвращающий `null`, если cookie уже отсутствовал — это НЕ ошибка (желаемое состояние и так достигнуто); раньше это могло попасть в список "неудач" безосновательно.

### Рассмотрено, но намеренно НЕ изменено

- **Разрешение `tabs` в manifest.json**: по документации Chrome, `chrome.tabs.query({url:...})` не требует permission `"tabs"`, если URL покрыт `host_permissions` (что у нас так и есть для всех twitch.tv-доменов), а `chrome.tabs.reload`/`sendMessage` вообще не требуют этого разрешения. Теоретически `"tabs"` можно убрать. Решил **не трогать** — это единственная точка отказа, ломающая ключевую функцию (перезагрузку вкладок после переключения), а живого ungoogled-chromium 149 под рукой для проверки нет. Экономия одного permission не стоит риска регресса основной функции без возможности протестировать.
- **Согласованность чтения при параллельно открытых попапах в разных окнах браузера**: `loadAccounts`/`getCurrentCookieUser` не проходят через очередь `runExclusive`, поэтому теоретически при ДВУХ одновременно открытых попапах (в разных окнах) один может увидеть промежуточное состояние во время переключения в другом. Это очень редкий сценарий (нужно буквально два окна с открытым попапом одновременно), и постановка чтения в очередь замедлила бы обычный `loadState()` без сильной практической пользы.

### Модель угроз (шифрование)

Ключ теперь **non-extractable CryptoKey** в IndexedDB — это существенно надёжнее хранения сырых байт, но не абсолютная защита:

- ✅ Защищает от копирования профиля браузера на другую машину и попытки вычитать ключ напрямую из файлов
- ✅ Защищает от кода вне расширения (другие расширения, сайты)
- ❌ **Не защищает** от кода, который выполняется в контексте самого расширения (например, через remote debugging с полным доступом к браузеру) — такой код может вызвать `decrypt()` через тот же API, что и сама эта функция
- ❌ Не защищает, если скомпрометирован сам браузер/ОС на уровне root/administrator

Это фундаментальное ограничение любого локального хранилища расширений без внешнего секрета (мастер-пароля). Полноценная защита потребовала бы пароля, который пользователь вводит при каждом открытии попапа — что противоречит цели «переключение в один клик».
